# 로컬 DB 성능 개선 검증 — 2026-09-12

`0042_performance_discovery.sql`은 새 글 저장 시 수신자별 알림을 생성하던 작업을 PostgreSQL 내부 배치로 옮긴다. 기존 앱의 RPC 인자·반환 형식, 관심/근처 알림 분류, 기존 푸시 큐와 ADR-0001 전체 안전 모니터링은 유지한다. 운영 DB에는 적용하지 않았다.

## 측정

동일한 별도 Docker 컨테이너에서 0041 기준 측정 → 0042/0043 적용 → 변경 후 측정을 순서대로 실행했다. Supabase Postgres 17.6 arm64, pg_cron 1.6.4. 준비 데이터는 트리거를 건너뛰어 생성하지만, **글 저장 시간은 모든 애플리케이션 트리거를 활성화한 상태**에서 측정했다. 쿼리마다 준비 실행 1회 이후 3회 중앙값이며, 모든 데이터는 합성 데이터다. 노트북의 다른 개발 작업에 의한 편차가 있어 운영 지연·동시 사용자 수를 보장하는 수치는 아니다.

10,000명 중 후보 500명을 처리한 배치는 약 135ms였다(단일 측정, 최초 함수 계획 포함). 총 알림 생성 비용이 사라지는 것은 아니며, 글 저장 트랜잭션에서 분리된다. 원본 샘플은 `performance-db-2026-09-12.json`, 재현 방법은 `scripts/performance/README.md`에 있다. 초기 탐색의 폐기된 카테고리 ID 2 대신 실제 카테고리 ID 4로 수정한 후 전체 전후 측정을 다시 실행했다. 위 표와 JSON만 최종 결과다.

## 유지한 구현

- 도시·카테고리·커서 부분 인덱스와 커스텀 쿼리 계획으로 선택된 카테고리에 맞는 페이지를 조회한다.
- 검색의 제목/본문, 작성자 닉네임/동네, 해시태그 조건을 개별 후보 조회로 나눠 각각 같은 접근 조건·순서·상한을 적용하고 합친다. 기존 제목/본문 trigram 인덱스를 재사용하고, 해시태그 prefilter 인덱스 1개를 추가했다. 원래 개별 해시태그 조건을 다시 검사해 서로 다른 태그를 가로지르는 검색 결과는 허용하지 않는다.
- 표현식 통계가 없으면 흔한 검색어도 희귀하다고 추정해 대량 정렬했다. 표현식 통계와 ANALYZE로 이를 수정했다. 그래도 세 검색 분기 때문에 흔한 검색에는 이 표 기준 약 6.7ms의 추가 비용이 있다. 희귀/없는 검색어의 수백 ms 지연을 없애는 데 따른 측정된 절충이다.
- 인기 해시태그는 동일 작성자·원문 태그를 먼저 중복 제거한 뒤 정규화한다. 서로 다른 원문이 같은 태그로 정규화되어도 작성자 수를 중복 계산하지 않는다. 사용자 차단 조건을 유지하며 공용 캐시를 추가하지 않았다.

## 알림 작업과 복구

신규 실제 공개 글만 큐에 1행 추가한다. 기존 글의 backfill이나 편집 시 재전송은 없다. 워커는 `FOR UPDATE SKIP LOCKED`로 작업을 잡고 호출당 **최대 후보 500명·글 10개**를 확인한다. 알림 삽입·기존 푸시 enqueue·수신자 커서 갱신은 같은 트랜잭션으로 커밋된다. 실패/연결 종료 시 모두 롤백되며 다음 실행에서 이어간다. 완료한 큐 행은 삭제되고 진행 중인 글은 마지막 처리 시각을 바꿔 다른 글에 순서를 양보한다. 사용자·글의 부분 유니크 인덱스가 중복 discovery 알림을 방지한다.

처리 시점에 공개 상태, 작성자/수신자 활성 상태, 예시/리뷰 계정, 동의·관심 주제·현재 저장 도시·차단·닫힌 모임을 확인한다. 큐 등록 후 바뀐 discovery 설정은 그 이전 글을 뒤늦게 받는 데 쓰이지 않는다. 내부 변경 시각은 기존 설정 JSON RPC에서 제외한다. 큐와 워커는 anon/authenticated에 공개하지 않는다.

기존 pg_cron에서 `gling-discovery-posts`가 10초마다 실행된다. 현재 후보는 전체 관심/근처 동의자이므로 기본 처리 상한은 초당 후보 약 50명이다. 10,000명의 동의자가 있는 단일 글도 전부 확인하려면 약 200초와 완료 확인 1회가 필요할 수 있다. 도시별 분할과 처리량 증가는 실제 큐 길이/지연을 보고 결정한다. 지금 설계는 무제한 fanout으로 저장 지연을 늘리지 않도록 하는 제한이며, 높은 글 생성률에서 backlog가 없다는 보장은 아니다.

운영 확인 SQL: 큐 행 수와 `min(enqueued_at)`, `cron.job_run_details`의 최근 실패/실행시간을 확인한다. SQL 에러는 삼키지 않아 pg_cron에 실패가 남는다. 지속 오류는 원인을 고친 뒤 다음 스케줄에서 같은 커서로 재시도한다. 클라이언트에는 수동 재전송 RPC가 없다.

## 검증과 범위

깨끗한 별도 DB에서 bootstrap 및 0001–0043 migration 재생 통과. 전체 SQL 회귀 576개 통과 후 추가한 작성자 비활성·리뷰 enqueue·모임 종료 3개도 통과(현재 총 579개). discovery 기존 계약 88개, 워커 20개, 검색/인기 태그 원본 정의와 동등성 15개, 채팅 0043의 12개가 포함된다. 두 DB 연결을 이용한 `check-worker-lock.py`는 다른 워커가 잡은 행을 500ms 제한 안에 건너뛰는 것을 확인했다. 중단된 배치 롤백, 커서 재개, 중복, 권한 차단 및 기존 푸시 enqueue도 검증했다.

Auth/Storage는 bare Postgres에서 SQL에 필요한 최소 스키마 계약으로 보완했다. 실제 GoTrue 로그인, Storage HTTP, APNs/Expo 전송과 모바일 네트워크 지연은 검증 범위에 포함되지 않는다. 성능 표의 피드 조회는 게스트 문맥이며, 로그인 사용자의 차단 정확성은 별도 SQL 회귀에서 검증했다. RLS·알림·안전 검토 등 애플리케이션 트리거는 실제 migration 코드다.

새 인덱스와 ANALYZE는 일반 migration 문장으로 실행된다. 운영 적용 시 인덱스 생성 동안 글쓰기 잠금과 I/O 비용이 발생할 수 있으므로 기존 배포 절차에 따라 적용해야 한다. 호환성 때문에 구버전 RPC를 제거하지 않았다.
