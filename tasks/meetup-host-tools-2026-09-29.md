# 모임장 도구 설계 계획 — 2026-09-29

## 목표와 현재 기반

모임장이 사람을 초대하고, 정원·신청·참여 인원을 관리하며, 모임의 분위기와 비용을 명확히 안내할 수 있게 한다. 소규모 술자리부터 페스티벌 동행까지 같은 기본 흐름을 쓴다.

현재 모임은 `posts.room_preview`와 `meetup_requests`로 운영된다. 정원은 호스트 포함 2~50명이고, 멤버십의 모임 자리는 **승인 시** 서버에서 검사한다. 승인된 사람에게 그룹 대화 접근을 준다. 게시글 공유 URL과 네이티브 공유 시트도 이미 있다. 이 구조를 확장하고 별도 초대·결제 시스템부터 만들지 않는다.

## 제품 결정

- **외부 초대:** 모임 상세의 기존 공개 게시글 링크를 공유한다. 받는 사람은 모임 정보와 호스트 프로필을 먼저 보고 로그인·가입한 다음 기존 참여 신청을 보낸다. 링크 방문이나 신청만으로 정원·멤버십 자리를 차감하지 않는다. 비공개 초대 링크는 실제 수요가 생길 때 별도 설계한다.
- **앱 안에서 직접 초대:** 유저 프로필에 `내 모임으로 초대`를 둔다. 호스트가 본인 모임을 고르면 상대에게 알림이 간다. 초대 수락 시에만 서버가 정원, 차단 관계, 계정 상태, 인증 조건, 상대의 멤버십 자리를 다시 검사한다. 거절·만료·취소는 자리를 쓰지 않는다. 상대가 수락하기 전 그룹 대화 접근도 없다.
- **모임장 관리:** 모임 상세에서 `모임 관리` 시트를 연다. 신청 대기, 참여 중, 초대 중을 분리하고 정원 `현재/최대`를 항상 보여준다. 정원 축소는 현재 참여 인원 미만으로 할 수 없다. 참여자 내보내기는 확인 및 알림을 거치고 그룹 대화 권한을 즉시 종료한다.
- **커스터마이즈:** 기존 제목·소개·커버·일정·신청 질문을 편집하되, 일정 변경은 참여자에게 변경 알림을 보낸다. 모임 성격을 드러내는 한 줄 분위기·집결 안내는 상세에 둔다. 정확한 집결 위치처럼 민감한 정보는 승인된 참여자만 보게 한다.
- **회비:** 첫 버전은 예상 비용과 `각자 결제/호스트 수금` 안내까지만 지원한다. 실제 송금·카드 결제·잔액 보관은 넣지 않는다. 이후 정산 기록을 만들더라도 누가 얼마를 부담했고 확인했는지의 장부부터 시작한다.
- **대규모 모임:** 현재 50명 상한을 단순히 올리지 않는다. 모집·대기열·공지·체크인과 그룹 채팅 부하를 별도 검증한 뒤 50명 이상을 위한 운영 모델을 만든다.

## 구현 순서

### 1. 외부 공유와 모임장 진입점 — 작은 변경

- [ ] 모임 상세에 호스트용 `초대 링크 공유`와 `모임 관리` 진입점을 둔다. 공유는 기존 `buildSharedPostUrl`과 `Share.share`를 재사용한다.
- [ ] 비회원이 링크를 열면 공개 모임 정보를 볼 수 있고, 참여 신청 시 로그인 안내로 이어진다.
- [ ] 만료·마감·삭제된 모임 링크에는 명확한 상태와 모임 목록으로 돌아가는 행동을 보여준다.
- 검증: iOS·Android·웹 링크 열기, 로그인 전후 복귀, 공유 취소, 차단/마감 상태. `npx tsc --noEmit`, `npm test`.

### 2. 정원과 참여자 관리 — 서버 권한 우선

- [ ] 호스트만 보는 관리 시트에 신청 대기/참여 중/초대 중 목록과 정원 표시를 제공한다. 기존 신청 승인·거절 RPC를 재사용한다.
- [ ] 정원 변경 RPC는 모임 행을 잠그고 `현재 참여자 수 ≤ 새 정원 ≤ 50`을 검사한다. 호스트가 아니거나 종료된 모임이면 거부한다.
- [ ] 내보내기 RPC는 참여 상태·멤버십 자리·채팅 접근을 한 트랜잭션에서 바꾸고 양쪽에 결과를 알린다. 재신청 정책도 서버에서 정한다.
- 검증: 두 호스트 동작의 동시성, 정원 축소/승인 경합, 내보낸 사용자의 새 메시지·과거 메시지 접근, 모임 자리 반환.

### 3. 앱 내 직접 초대 — 수락에서만 자리 차감

- [ ] `meetup_requests`에 초대 대기 상태를 추가하거나 그와 동등한 작은 서버 모델을 둔다. `호스트 → 특정 유저 → 특정 모임` 관계, 만료, 취소, 중복 방지를 저장한다.
- [ ] 프로필의 초대 행동은 호스트 소유 모임만 선택 가능하게 하고, 상대의 알림에서 모임 상세와 `수락/거절`을 제공한다.
- [ ] 수락 RPC는 모임 행 잠금 아래 정원·인증·차단·계정·멤버십 자리를 다시 확인한 뒤 승인 상태와 그룹 대화 권한을 함께 확정한다. 실패하면 초대는 유지하고 이유를 보여준다.
- 검증: 초대만 받은 상태에서는 자리/정원 미차감, 동시 수락으로 정원 초과 불가, 중복 알림 없음, 거절/취소/만료, 차단·탈퇴 후 권한 회수.

### 4. 모임 편집과 비용 안내 — 운영 피드백 이후

- [ ] 제목·커버·설명·일정·신청 질문 수정 범위를 정하고, 변경 이력을 남긴다. 일정 변경은 참여자에게 알린다.
- [ ] 예상 비용·결제 방식·환불/취소 안내를 정보로 표시한다. 금전 거래 기능이 필요하다는 실사용 증거가 쌓이면 정산 장부와 결제를 별도로 설계한다.
- 검증: 수정 권한, 이미 승인된 멤버에게 변경 전달, 긴 제목·비용 미정·일정 취소 상태, 안전 모니터링과 관리자 감사 경로 유지.

## 화면 원칙과 근거

모임 상세의 기존 화면과 피드백 패턴을 유지한다. 관리 정보는 참가자 목록, 초대 목록, 정원을 한 시트에 모으되 신청/참여 상태는 명확히 구분한다. [LinkedIn의 참가자·초대 탭](https://mobbin.com/screens/7c814a33-edcd-4bd3-8ab6-325fe7c08422)과 [Luma의 정원 설정](https://mobbin.com/screens/31952f6c-2f6b-445c-8e53-efccdd0e0670)을 정보 구조 참고로 삼고, 색·타이포·모션은 글링의 현재 다크 브랜드를 따른다. 새 컨트롤에는 `useInteractionFeedback().play(...)`를 적용한다.

안전 모니터링과 권한 있는 관리자 검토는 [ADR-0001](../docs/decisions/0001-safety-monitoring-and-admin-access.md)의 기존 범위를 유지한다. 초대 링크가 비공개 대화나 개인정보 접근을 부여하지 않도록 서버 권한으로 검증한다.
