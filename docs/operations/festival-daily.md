# 도시별 페스티벌 갱신

2026-10-13 사용자 정정: 메인은 ‘전체 보기’와 같은 도시의 행사 중 시작 시간이 가까운 최대 7개를 갤러리로 보여준다. 이름에 festival이 들어가는 행사로 제한하지 않는다. 같은 이름·공연장·시작 시각의 중복 티켓만 합치고 날짜가 다른 일정은 유지한다. 지난 행사, 취소·연기된 행사, 시간이 확정되지 않은 행사는 제외한다. 7개가 없으면 실제 등록된 수만 보여준다. 기존 운영자 지정 칸은 우선한다.

현재 수정은 로컬 소스와 검사까지만 진행한다. 사용자가 한 번에 처리하겠다고 지시했으므로 커밋·push·빌드·export·운영 배포·스토어 제출을 실행하지 않는다. 취소한 1.2.2 릴리스를 자동 재개하지 않는다.

후속 지시로 최신 미커밋 코드를 시뮬레이터에 띄우는 로컬 Debug 실행은 진행한다. 스토어용 빌드·운영 배포·제출 보류는 유지한다. 기존 `mobile`의 8081 서버는 보존하고 이번 체크아웃의 8083 서버를 사용한다.

개발용 바이너리는 네이티브 빌드 번호가 그대로여도 최신 JS를 리로드한다. `__DEV__` 실행만 해당 번호의 강제 업데이트 검사에서 제외하고, 기존 개발 런타임에 현재 소스를 연결한다. 스토어용 Release의 시작·화면 복귀 검사와 네트워크 오류 시 차단은 유지한다. 웹·Expo Go가 화면 복귀 후 검사 중 상태에 남는 문제도 함께 수정했다. 새 네이티브 바이너리가 완성됐다는 뜻은 아니다.

`tm-festival:<city>` 캐시는 도시 현지 자정까지 공유한다. 서머타임 종료일도 같은 현지 날짜 동안 한 번 수집한다. 현재 5개 도시의 기본 수집은 하루 5회의 Ticketmaster 검색이다. 한 번에 최대 100개 후보를 읽으며, 목록 밖의 수동 지정 행사만 상세 호출이 추가될 수 있다. 다른 행사 검색·날짜·월·상세 캐시의 15분 주기는 유지된다.

기존 `gling-trending-notifications` 작업의 5분 실행과 도시 순환을 재사용한다. 새 일자에 방문자가 먼저 오면 원자적 갱신 선점으로 즉시 수집하며, 다른 요청은 같은 수집을 중복 실행하지 않는다. 방문자가 없어도 기존 작업이 순환하며 수집한다. 알림을 꺼도 페스티벌 수집은 계속된다. 수집 실패는 성공한 빈 목록으로 저장하지 않으며 15분 후 재시도할 수 있다. 카드 순환은 API를 호출하지 않는다.

앱과 공개 웹은 기존 공용 조회 함수를 함께 사용한다. 일일 조회가 일시적으로 실패하거나 유효 카드가 7개 미만이면 동일 도시의 ‘전체 보기’ 첫 페이지로 보충하므로 이전 서버·좁은 옛 캐시에서도 가까운 행사를 선택한다. 같은 ID는 두 응답의 `fetchedAt` 중 최신 값을 사용하고 수동 지정은 유지한다. 일일 응답만으로 7개가 되면 추가 요청은 없다. 보충 조회가 실패하면 정상 빈 목록으로 처리하지 않고 재시도 안내를 보여준다.

## 원하는 칸에 지정

별도의 제휴 전용 칸 없이 1–7번 중 아무 칸에 지정한다. 현재 구현은 Ticketmaster 행사 ID를 사용한다. 해당 도시의 상세 응답을 먼저 조회하면 목록 밖 행사도 기존 캐시에 저장된다.

기존 관리자 클라이언트의 로그인과 2차 인증(AAL2)을 완료한 상태에서 다음 RPC를 사용한다. 서버가 관리자·도시·행사·기간을 검증하고 기존 관리자 감사 기록을 남긴다.

```ts
await client.functions.invoke('ticketmaster-events', {
  body: { cityId: 'vancouver', eventId: 'OWNER_CHOSEN_EVENT_ID' },
});
await client.rpc('set_admin_festival_slot', {
  p_city_id: 'vancouver', p_slot: 3,
  p_event_id: 'OWNER_CHOSEN_EVENT_ID', p_ends_at: null,
});
await client.rpc('get_admin_festival_slots', { p_city_id: 'vancouver' });
```

`p_ends_at`으로 노출 종료 시간을 지정할 수 있다. 생략하면 행사 시작까지 유지한다. 행사 시작 이후로는 늘릴 수 없다. 같은 페스티벌을 다른 칸에 지정하면 기존 칸에서 이동한다. 동일 도시의 관리자 변경은 기존 도시 행을 잠가 동시에 중복 저장되지 않는다. 이름·공연장·연도의 식별 해시도 저장해 이전 API 캐시가 만료된 뒤에도 다른 날짜 티켓을 같은 페스티벌로 이동한다. 원문 데이터는 추가 저장하지 않는다. `p_event_id: null`로 해제하면 자동 선택으로 돌아간다. 변경은 다음 목록 조회부터 적용된다.

앱은 화면 포커스·포그라운드, 웹은 포커스·다시 표시될 때 목록을 재조회한다. 같은 도시에서는 보고 있던 행사 ID를 유지하며, 사라진 행사나 새 도시는 첫 카드부터 보여준다. 열린 화면도 현지 날짜 변경, 행사 시작, 지정 만료를 분 단위로 확인한다. 조회 실패 후에는 기존 서버 선점 제한과 맞춰 15분 후 다시 시도한다. 새 데이터 수집과 기존 캐시 조회는 별개다. 메인 카드 위의 작은 이전·다음 버튼과 스와이프는 API 호출 없이 일곱 카드를 순환한다. 직접 넘기면 자동 넘김을 20초 멈추며, 모션 줄이기와 화면 읽기 설정을 유지한다. 카드 아래의 ‘다가오는 일정’과 일곱 썸네일 줄은 제거한다. 그 아래 공간은 도시 인기 장소 진입 영역으로 사용하되, 실제 장소·인기 순위 API가 연결되기 전에는 미연결 상태를 표시한다.

## 검증과 복구

기존 일일 수집·운영자 지정 migration 두 개는 이미 운영에 있으므로 다시 실행하지 않는다. 차후 일괄 배포를 지시받으면 앱·공개 웹의 선택 함수와 `ticketmaster-events`를 함께 배포하고, 새 함수가 저장된 것을 확인한 뒤 `20261013230000_festival_gallery_cache.sql`로 좁은 옛 후보 캐시 5개만 만료시킨다. 기존 수집 작업이 새 후보를 채우며, 캐시 본문·수동 지정·다른 검색 캐시와 작업 소속은 보존한다. 이전 앱은 자체 이름 필터가 있으므로 서버만 바꾸면 새 갤러리가 완성되지 않는다. 미관련 migration을 일괄 push하지 않는다.

SQL 검사는 `supabase/tests/festival_daily.test.sql`과 `supabase/tests/festival_gallery_cache.test.sql`을 기존 로컬 DB의 트랜잭션에서 실행하고 롤백한다. 행 잠금 검사용 기본 PostgreSQL `pgrowlocks` 확장도 테스트 트랜잭션에서만 만들며 운영에는 설치하지 않는다. 신규 스키마·관리자 RPC 변경은 없다.

2026-10-11 운영 배포·캐시·작업 소속·API 재조회 증거와 복구 SQL은 작업 기록의 `output/qa/festival-daily-2026-10-11/`에 보관한다. 복구는 백업한 Edge Function을 먼저 복원하고 `rollback.sql`로 기존 수집 함수·뷰·정리 작업을 복원한다. 수동 지정 데이터와 migration 이력은 삭제하지 않는다.

2026-10-13 조회 기준 공개 iOS와 Android alpha는 1.2.0(64)이며, 보류된 1.2.2 실행의 서명 빌드 완료·새 제출은 확인되지 않았다. 소스 반영, 검사, 서버 배포, 웹 배포, 스토어 심사 제출, 사용자에게 실제 공개된 버전은 각각 확인한다.

2026-10-13 후속 실행 기록: 확인된 일괄 반영 승인 아래 사진 묶음·행사 알림 migration, 기존 `ticketmaster-events`·`push-notifications` 함수와 캐시 만료 migration은 운영 반영·재조회했다. 이후 사용자가 다시 빌드 전에 실제 시뮬레이터를 보라고 지시했으므로 현재는 추가 커밋·빌드·태그·배포·제출을 모두 보류한다. 앞의 차후 배포 절차는 이미 수행한 부분을 중복 실행하라는 지시가 아니다. 최신 클라이언트 실조회는 다섯 도시 모두 가까운 행사 7개를 확인했으며, Vancouver의 일일 조회 429는 같은 도시 전체 보기의 정상 응답으로 보충했다. 새 네이티브 바이너리는 만들지 않고 기존 설치 앱을 8083의 최신 JS로 다시 열었다.
