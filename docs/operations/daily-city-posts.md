### 왜 복사 단계가 필요한가

macOS가 `~/Desktop`을 보호해서 launchd로 도는 프로세스는 데스크톱 안 파일을 열지 못한다
(`Operation not permitted`). 그래서 원고를 `~/Library/Application Support/gling/city-posts/payload/<날짜>.json`
으로 복사해두고 예약 실행은 그 사본을 읽는다. 같은 이유로 `scripts/backup-db.sh`도 launchd에서 계속 실패한다.

두 곳 모두 시스템 설정 → 개인정보 보호 및 보안 → 전체 디스크 접근 권한에 `/bin/bash`를 추가하면
복사 단계 없이 저장소 파일을 직접 읽게 만들 수 있다. 권한을 주지 않을 거면 지금 방식(복사)을 유지한다.

## 글 검수 — Patina 필수

사람처럼 읽히는 모든 글은 작성 agent 안에서 설치된 Patina 스킬을 적용한다. 소재 확인→작성자 상세 설정/최근 글→초안→Patina 교정→의미·사실·말투·중복 확인→기존 예약 큐 순서다. `content/<날짜>/patina-review.json`에 글별 작성자ID·원문/최종본문 SHA256·교정 내용·의미/캐릭터 판정을 남긴다. 실제 교정/검수 없이 파일이 있다는 이유만으로 통과를 주장하지 않으며 이미 승인/공개된 글을 재작성하거나 새 backend/worker/유료 호출을 만들지 않는다.

## 원고 형식

```json
{ "posts": [
  { "ord": 1, "city_id": "vancouver", "author_nickname": "스카이트레인통근", "tag_slug": "transport",
    "title": "Vancouver의 Kitsilano 산책", "body": "Kitsilano에서 산책할 곳을 찾고 있다면…",
    "source": "https://확인한-공식안내", "place_name": "Kitsilano", "place_address": "" }
]}
```

- `city_id`: vancouver, toronto, montreal, edmonton, calgary (앱에서 열린 도시). 도시를 열면 `cities.is_open`을 켜고 그 도시 프로필을 5개 이상 만들어야 한다.
- `author_nickname`: 그 도시의 활성 시드 프로필 닉네임. 원고 작성 전에 정한다. 없거나 중복되면 등록 전체가 실패한다.
- `tag_slug`: life, travel, food, education, transport, settlement
- `source`: 일반 글은 실제로 확인한 공식 안내, 사연은 실제로 본문을 읽은 원문 주소다. 내부 검증용으로만 남기고 읽기 본문에는 넣지 않는다.
- 장소·동네·도시·업체·기관 등 고유명사는 실제 공식 영문/로마자 철자로 쓴다. 첫 언급에 `Kitsilano, Vancouver`, `Dineen Coffee Co., Toronto`처럼 검색할 수 있는 이름을 넣고 설명은 기존 한국어 말투를 유지한다. Montréal의 공식 불어 이름은 원문 철자를 유지하며 임의 영어 번역이나 추측한 스펠을 만들지 않는다.
- `place_name`, `place_address`: 실제 장소를 소개할 때만 확인한 공식 이름과 주소를 넣는다. 이름은 제목/본문에도 정확히 있어야 한다. 주소가 미확인이면 빈 문자열로 남기고 이름·도시로 검색한다. 일반 정책/생활 안내에는 이 필드를 생략한다. 한 글의 지도는 주된 장소1곳만 연결한다.
- 일일 준비가 `place_name + place_address + 해당 도시 + Canada`를 URL 인코딩해 `https://www.google.com/maps/search/?api=1&query=...`를 만든다. 기존 `Google 지도:` 저장 마커/`postMapBody`/44px `PostMapLink`를 재사용하여 URL은 읽기 본문에서 분리하고 버튼으로 보여준다. Google Maps 앱이 있으면 앱, 없으면 웹 검색으로 열린다. API키·SDK·새 위치권한은 필요하지 않으며 임의 좌표/Place ID를 넣지 않는다. [Google 공식 Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)

## 스크립트가 지키는 것

- 원고에 지정한 도시별 기존 프로필을 재사용한다. 새 프로필을 만들지 않는다.
- 시드 계정(`@seed.gling.invalid`)만 쓴다. 운영자·테스터의 실제 계정에는 대신 쓰지 않는다.
- 프로필 도시와 글 도시를 섞지 않는다. 몬트리올 글은 몬트리올 프로필로만 간다.
- 예약 시각과 실제 등록 시각을 구분한다. `created_at`은 실제 저장 시각이고 `posted_on`은 그 도시의 현지 날짜다.
- 새 목표는30건/도시별 일반5건+사연1건이다. 기존25건/도시별 일반5건 큐도 보존하며 같은 날짜 큐는 다른 원고로 덮어쓰지 않는다. 원래 제출·영수증을 먼저 대조해야 한다.
- `receipts/<날짜>.json`에 HTTP 호출 전에 attempted를 저장하고 실제 DB 글 id·도시·제목·created_at 재조회 후 confirmed로 바꾼다. HTTP 실패나 빈/잘못된 응답은 성공으로 보고하지 않고 attempted를 보존한다. 확인 안 된 제출을 다시 보내지 않는다. 중앙은 이 원고·영수증과 운영 DB를 읽어 미확인/미게시를 따로 정리한다.
- 새 글 조회수는 0으로 들어간다.
- `GROW=1`은 원고·글 등록·게시 영수증 없이 행정 조회수만 증가시킨다. toronto/vancouver/montreal/calgary/edmonton의 공개·미삭제 글 중 실제 생성 시각부터30일 미만인 글만 대상이다. 미래 글·삭제/비공개 글·30일 이상 된 글은 건드리지 않는다. 생성 시각부터24시간씩 나눈 일차와 기존 글 id/일차 해시로 1~14일차는 하루1~30개, 15~30일차는 하루1~8개의10분 구간을 고른다.
- 선택 구간은 하루144구간에55칸 간격의 순열로 분산한다(55와144는 서로소). 현재 구간이 선택됐을 때만 기존 조회수에1을 더한다. 게시 직후 첫 부분 구간과 이미 지나간 구간은 보충하지 않으므로 복구 첫 회차에 누락된 며칠치를 한꺼번에 올리지 않는다. 이미 높은 실제 조회수나 어드민 수치도 줄이지 않는다. 기존 어드민 상한100,000,000 이상은 증가하지 않아 큰 기존 값의 정수 넘침을 막는다. DB 행 잠금으로 다른 작업이 잠근 글은 건너뛴다.
- 실제 증가1건과 현재10분 `private.post_view_pulse` 삽입1건은 같은 트랜잭션이다. 기존 `(post_id,bucket)` 기본키 충돌이면 증가하지 않으므로 같은 구간의 재실행·동시 작업은 중복되지 않는다. 해당 구간에 실제 비로그인 pulse가 있어도 행정 증가를 생략한다. 과거 버킷과 실제 로그인 조회인 `public.post_views`는 읽거나 쓰지 않는다. pulse에는 실제 비로그인 조회와 행정 증가가 함께 있으므로 pulse 합계나 표시 조회수를 실제 독자 수·자연 성장으로 보고하지 않는다. pulse 잠금은250ms, SQL은20초 한도이며 실패하면 해당 증가 트랜잭션 전체를 되돌린다.
- 같은 도시에 같은 제목이 이미 있으면 그 줄은 건너뛴다. 여러 번 돌려도 중복이 생기지 않는다.
- 댓글·답글은 자동으로 만들지 않는다. 실제 글과 앞선 대화, 작성자 캐릭터를 보고 도움이 되는 내용만 개별 작성한다. 회원 글에도 개수 채우기용 댓글을 붙이지 않는다.

## 운영 DB 읽고 쓰기

psql이 없어서 Supabase Management API를 쓴다. 토큰은 키체인의 `Supabase CLI` 항목에 있다.

```sh
jq -Rs '{query: .}' <<'SQL' | curl -s -X POST \
  "https://api.supabase.com/v1/projects/wjvahbdwmctzpkndqaxa/database/query" \
  -H "Authorization: Bearer $(security find-generic-password -s 'Supabase CLI' -w)" \
  -H "Content-Type: application/json" --data-binary @-
select p.city_id, p.title from public.posts p
where p.status='published' order by p.city_id, p.created_at;
SQL
```

결과는 `[{"...": "..."}]` 형태의 JSON으로 온다. 여러 문장을 한 번에 보내면 마지막 문장의 결과만 오므로 한 번에 하나씩 보낸다.

## 손으로 돌릴 때

```sh

STAGE=1 scripts/seed-city-posts.sh <날짜>     # 수동 원고를 그대로 복사; 예약 큐로 자동 게시하지 않음
```

실제 SQL의 반복·동시 실행과 실제 조회/버킷 보존 검사는 이미 실행 중인 로컬 Postgres 컨테이너에만 `CITY_POSTS_TEST_CONTAINER=<컨테이너ID> node --test scripts/seed-city-posts.test.mjs`로 한다. 테스트는 임시 데이터베이스를 만들고 끝에 삭제한다. 운영 DB나 새 컨테이너를 사용하지 않으며 앱/SNS 글을 시험 게시하지 않는다.

## 수동 요청

자동 회차와 별개로 요청이 오면 같은 파이프라인을 그대로 쓴다. 날짜·도시·건수를 지정할 수 있다.

1. `content/<날짜>/posts.json` 을 새로 쓰거나 도시·건수를 바꿔 쓴다. 각 글의 `author_nickname`을 먼저 지정한다. 기존 날짜에 이어 쓰는 경우 같은 도시 같은 제목은 자동으로 건너뛴다.
2. `STAGE=1` 로 복사하고 `scripts/seed-city-posts.sh <날짜>` 로 등록한다.
3. 등록 후 확인한다. 실제 도시별 건수·작성자 도시·등록 시각·중복 여부와 읽기 본문에 출처가 없는지. 지도 저장 마커는 기존 지도 버튼으로 분리되는지 확인한다. 수동 즉시 등록은 일일 랜덤 예약과 별도이며 기존 허가된 요청만 실행한다.

사진을 붙이는 경우에는 아래를 함께 본다.

## 사진

글에는 사진을 최대 4장까지 붙일 수 있다. 앱과 같은 규칙을 따른다.

- 버킷: `post-images`, 형식: jpeg·png·webp, 장당 5MB 이하
- 경로: `<작성자 id>/<타임스탬프>.<확장자>` (앱의 `buildPostImagePath` 와 같은 형식)
- `posts.image_paths` 에 그 경로를 넣는다
- 공개 읽기 정책이 "그 이미지를 참조하는 공개 글이 있고, 경로 첫 칸이 글 작성자 id" 일 때만 열리므로 사진은 반드시 그 글 작성자 폴더에 올려야 한다

업로드는 RLS 때문에 작성자 본인 세션 또는 서비스 롤 키가 필요하다. 시드 계정 세션은 없으므로 서비스 롤 키를 키체인에 두고 쓴다. 키는 저장소·보고서·채팅에 남기지 않는다.

## 2026-10-15 최신 정정 — 도시 글은 그 사람의 말로 쓴다

사용자: “너무 ai티가 많이나잖아 스레드처럼 뭔가 인간미넘치게 써야함. 페르소나도 반영해서 지금 누가봐도 ai들이 글채우고잇는느낌”. 아래 옛 형식 지침과 충돌하면 이 절을 우선한다. 기존 G6·도시별 일반5건/사연1건·작성자/공개 표시·출처 검증·게시 권한·고정 큐/시도 영수증·일정은 유지한다.

- 글을 쓰기 전에 실제 선택한 페르소나와 같은 작성자의 최근 글3개를 읽는다. 직업·생활·관심사 중 이 소재를 고른 이유와 말투 근거를 내부 검수에 남긴다. 닉네임만 바꿔 같은 문장을 배정하지 않는다. 가족·도시·직업·관계 설정은 바꾸지 않는다.
- 일반 글도 먼저 그 사람의 궁금증·판단·취향·고민 중 하나를 잡는다. 지역 사실은 그 말을 뒷받침하는 만큼만 쓴다. 공식 안내는 사실 확인 자료이며, 매일25개 공지문을 요약해야 한다는 뜻이 아니다. 실제 읽은 지역 원문도 소재로 쓸 수 있고, 일정·요금·절차는 필요할 때 공식 자료로 검증한다. 출처/관측시각은 내부에 보존한다.
- 같은 도시 글을 교통·도서관·시청 공지로만 채우지 않는다. 먹거리·주거·일·관계·취미·동네 선택 등 실제 화자의 관심을 넓게 본다. 특정 요일마다 같은 기관/주제 묶음이나 같은 순서를 복제하지 않는다.
